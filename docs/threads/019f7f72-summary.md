## 一、项目目标

`f1-box` 的定位是一个 F1 比赛周末信息中心，面向用户提供当前赛季的结构化、易浏览数据，包括：

- 赛季概览和完整赛历
- 下一站比赛信息与倒计时
- 每站排位赛和正赛结果
- 车手积分榜和车队积分榜
- 数据来源、更新时间和新鲜度

产品希望由 LLM 与自动化持续维护。开发过程采用小步迭代，强调代码和文档简洁、高效、易维护；允许根据实际情况调整架构，不追求过早的复杂设计。

## 二、已确定的产品与工程方向

### 产品体验

- 第一版先聚焦当前赛季，不提前扩展历史检索等复杂能力。
- 使用原创的深色 `Night Grid` 视觉系统，体现速度感和竞赛感。
- 采用速度线、倾斜切角、紧凑数字排版和轻量动效。
- 不使用官方 F1 Logo、官方图片或依赖生成图片作为产品素材。
- 页面需要同时覆盖桌面端和移动端。

### 数据与部署架构

采用 R2-first 路线：

`Jolpica → Python 定时采集 → R2 版本化 JSON → Astro/Cloudflare Worker`

选择该路线的原因：

- 数据发布与前端部署解耦
- 版本化对象便于缓存和回滚
- manifest 指针可实现原子更新
- 第一版不需要为查询场景引入 D1、ORM 和事务复杂度

D1 暂缓到真正出现历史检索、跨赛季查询或复杂筛选需求时再引入。

访客请求不应直接访问上游 F1 数据源；上游数据应由采集任务预先获取、校验和发布。

## 四、采集、发布和 Web 层的进展

### 采集与发布

已规划并部分实现的核心不变量：

- Python 采集使用异步受限并发和瞬态失败重试
- 上游响应保留内容寻址的原始快照
- 归一化结果必须通过共享 Schema
- 失败时不能覆盖最后一个有效输出
- 相同 payload 应生成相同字节和 checksum
- checksum 应用于不可变对象路径
- 同名对象不能被覆盖；内容一致时复用，内容不一致时报错
- latest manifest 只保存当前版本指针，并最后更新

审阅过程中发现并要求处理了 checksum、freshness、响应身份、空分类和不可变对象等边界问题。

### Astro/Cloudflare Web 层

Task 4 已完成并通过 Astro check/build 及独立审阅，核心方向包括：

- 本地开发显式读取 fixture
- 生产环境从 R2 binding 读取 manifest 和 payload
- manifest 与 payload 做双层校验
- freshness 在读取时动态计算，避免把过期状态写死在存储对象中
- 页面层只依赖清晰的 `SeasonRepository` 接口
- Cloudflare Worker 使用生成的 Wrangler 类型和正确的 `env` binding 边界
- Ajv 运行时代码生成不放在 Cloudflare workerd 请求路径中，改用构建期预编译产物

页面组件已经按职责拆分为 Header、下一站、赛季轨道、单站信息、积分榜、结果表、新鲜度、Footer 和状态页等部分。

## 六、图片生成探索结论

曾尝试使用 Image Gen CLI 和 Cloudflare 图像模型生成四套页面概念，但最终没有采用生成结果：

- OpenAI 请求因区域限制返回 `403 unsupported_country_region_territory`
- Cloudflare 多个模型生成的内容存在文本失真
- 生成结果加入了赛道照片、旗帜、假导航和通用卡片墙等不符合约束的内容
- 这些结果不能作为高质量 UI 实现依据

最终决定停止继续试错，改为使用真实数据和代码原生 HTML/CSS 生成可控的视觉概念。这条路径更符合产品要求，也避免增加图片依赖和线上体积。
